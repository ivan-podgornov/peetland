# @peetland/npc

NPC: склеивает актора, инвентарь, психику, потребности, зависимости и HTN-агента, который каждый
тик планирует и исполняет задачи. Собирает NPC из данных фабрика NPC.

## Состояние и контекст

- **Состояние** (`NpcState`) — тип NPC, слепок актора и сами инвентарь, психика, потребности,
  зависимости и время, доступные только на чтение (`IReadonlyInventory`, `IReadonlyPsyche`,
  `IReadonlyNeeds`, `IReadonlyAddictions`, `IReadonlyTime`), а также знание о видимых NPC
  (`state.world.getVisibleNpcs(radius)`). С ним HTN-агент планирует задачи. Эффекты задач состояние не меняют: сущность,
  которую нужно поменять, задача клонирует (`clone()`) и кладёт копию в новое состояние. Время
  идёт, и его геттеры могут вернуть разное даже за одно планирование, а копия времени стоит на
  месте, пока её не выставят.
- **Контекст** (`NpcContext`) — живые актор, инвентарь, психика, потребности и зависимости, которым задачи
  отдают команды.

## Потребности

Начальные значения потребностей лежат в `NpcData.needs`. Фабрика NPC создаёт потребности
фабрикой `INeedsFactory` со временем, которое NPC знает о мире в момент создания: с него потребности и начинают
падать. Значения потребностей читаются на момент времени из того же состояния:
`state.self.needs.get(need, state.world.time)` (см. [потребности](../needs/CONTRIBUTING.md)).

Если NPC ушёл в долгое дело, срочная потребность не должна ждать конца плана. Поэтому фабрика NPC
создаёт фабрикой `IUrgencyWatcherFactory` наблюдателя срочности, и NPC каждый тик перед тем, как
продвинуть HTN-агента, проверяет им потребности из состояния. Если потребность только что стала
срочной, NPC мягко останавливает текущий план (`softStop`): агент доделывает транзакции и в том же
тике перепланирует, а слой потребностей корневой задачи планирует её удовлетворение. Пока
потребность срочная, повторной остановки нет.

## Зависимости

Начальные значение и сила каждой зависимости лежат в `NpcData.addictions`. Фабрика NPC создаёт
зависимости фабрикой `IAddictionsFactory` с тем же временем, что и потребности: с него и растёт
тяга. Значения зависимостей тоже читаются на момент времени из того же состояния (см.
[зависимости](../addictions/CONTRIBUTING.md)). Наблюдатель срочности за зависимостями не следит:
тяга не прерывает план, а ждёт следующего планирования.

## Сборка

`NpcFactory` — точка сборки пакета. Она создаёт актора, инвентарь, психику, потребности,
зависимости, наблюдателя срочности и HTN-агента с корневой задачей из данных NPC и передаёт их
`Npc` готовыми. Снаружи фабрике нужны только акторы, тики, сигнал завершения игры, знание о мире
и фабрика корневых задач, остальное она собирает сама.

## Корневая задача

NPC не зависит от задач. Корневую задачу HTN-агента получает фабрика NPC от фабрики
`IRootTaskFactory`, которую объявляет сам и получает в зависимостях. Какую реализацию передать,
решает тот, кто создаёт NPC. Фабрика создаёт каждому NPC своё дерево задач, и между NPC дерево не
делится.

Деятельность NPC зависит от его типа, поэтому `npc` объявляет и фабрику деятельности одного типа
`IActivityTaskFactory`. Её реализует пакет с задачами этого типа, например `homeless`, а собирает
корневую задачу из слоёв мир (см. [корневую задачу](../world/CONTRIBUTING.md#корневая-задача)).

## Связь актора и NPC

Актор NPC — его тело: он создаётся фабрикой игры и живёт в реестре акторов `@peetland/game`,
сам NPC отдельно. Чтобы перевести тело обратно в личность — например, по видимым акторам из игры
узнать, какие это NPC, — существует реестр связей «актор ↔ NPC». Интерфейсы `INpc` и
`IActorNpcRegistry` объявляет `npc`, потому что они потребляются NPC: `INpc` — публичный интерфейс
личности, через него с ней работает реестр. Переводы реестра бросают ошибку, когда сущности
в реестре нет: это ошибка вызывающего кода.
В конструкторе NPC связывает в реестре своего
актора с собой. Сигнал жизни NPC — часть его публичного API: когда NPC деспавняется, сигнал
прерывается, и реестр убирает связь.
Акторы без личности (случайные педы) в реестре не появляются. Какую реализацию передать, решает
тот, кто создаёт NPC: пакет `world` даёт `ActorNpcRegistry` (см.
[мир](../world/CONTRIBUTING.md#связь-актора-и-npc)).

## Для тестов

Точка входа `@peetland/npc/dev` даёт builder состояния NPC (`NpcStateBuilder`), контекст NPC
(`createNpcContext`), данные и зависимости NPC (`createNpcData`, `createNpcDeps`), мок реестра
связей (`createMockedActorNpcRegistry`) и мок фабрики NPC (`createMockedNpcFactory`).

`NpcStateBuilder` собирает состояние по шагам: задаёте только то, что важно для теста, а остальное
заполняется незначимыми значениями. NPC — бомж, стоит в начале координат, инвентарь пуст,
потребности удовлетворены полностью, зависимостей нет, а в мире полночь первого дня. Психику собирает
`PsycheBuilder` из `@peetland/psyche/dev`: `withPsyche` получает функцию, которой передаётся новый
билдер психики, а то, что она вернёт, ляжет в состояние. Потребности так же собирает `NeedsBuilder`
из `@peetland/needs/dev`: `withNeeds` получает функцию, которой передаётся новый билдер потребностей
со временем из состояния, а вернуть она может и мок потребностей. Зависимости точно так же
собирает `AddictionsBuilder` из `@peetland/addictions/dev` через `withAddictions`. `withKind` задаёт
тип NPC.

```ts
import { Addiction } from '@peetland/addictions';
import { Item } from '@peetland/inventory';
import { Need } from '@peetland/needs';
import { NpcStateBuilder } from '@peetland/npc/dev';
import { Feeling, Trait } from '@peetland/psyche';

const state = new NpcStateBuilder()
  .withPosition(10, 20, 3)
  .withAngle(90)
  .withInventory({ [Item.Money]: 50 })
  .withPsyche((psyche) => psyche.withTrait(Trait.Luck, 80).withFeeling(Feeling.Shame, 30).build())
  .withNeeds((needs) => needs.withValue(Need.Satiety, 10).build())
  .withAddictions((addictions) =>
    addictions
      .withStrength(Addiction.Alcoholism, 100)
      .withSatisfaction(Addiction.Alcoholism, 20)
      .build()
  )
  .withTime({ day: 1, hours: 20, minutes: 0 })
  .build();
```

Если тесту не важно ни одно поле, хватит готового состояния по умолчанию:

```ts
const state = NpcStateBuilder.default();
```
