# Комментарии в коде

Комментарий в коде отвечает на вопрос, на который не отвечают сам код, тесты и CONTRIBUTING пакета.
Всё остальное в комментарий не пишется: оно уже есть в другом месте и, когда код поменяется,
комментарий начнёт врать.

## TSDoc

TSDoc у класса, интерфейса, типа, метода или поля говорит, **что это**, одной-двумя фразами. Как
сущность устроена и почему так, описывается в CONTRIBUTING пакета, а как она себя ведёт в каждом
случае — в тестах.

В TSDoc не пишется:

- **Пересказ реализации.** Шаги алгоритма, порядок методов с их предусловиями, формулы, пороги и
  другие числа видны из кода, а случаи — из тестов.
- **Повтор CONTRIBUTING.** Если абзац TSDoc можно вставить в CONTRIBUTING без правок, ему место там.
- **Механика языка и инструментов.** Как TypeScript сужает тип, зачем нужен каст, как работает
  Vitest. Комментарий пишется для того, кто будет менять предметную область, а не для компилятора.
- **Ссылки на issue и пулл реквесты.** Issue закрываются, а комментарий остаётся. Если временное
  решение важно, оно описывается в CONTRIBUTING, а не в коде.
- **То, что и так сказано в имени.** У `PlaceType.MealSpot` или `BOTTLE_PRICE` комментарий,
  который повторяет имя другими словами, не нужен.

Пропущенный TSDoc лучше раздутого: у очевидного члена класса комментария может не быть вовсе.

## Комментарии внутри кода

Комментарий внутри функции объясняет, **почему** код такой, если это не видно из него самого:
неочевидное ограничение, обход платформы, причина порядка действий. Что код делает, комментарий не
пересказывает.

## Примеры

Плохо — TSDoc пересказывает алгоритм и повторяет CONTRIBUTING:

```ts
/**
 * Попрошайничать: один заход к ближайшему месту для попрошайничества. NPC сидит с анимацией и раз в
 * секунду с шансом BEGGING_CHANCE получает подачку BEGGING_REWARD. Каждая попытка — поступок
 * Deed.Begging, от которого растёт стыд. За заход NPC планирует столько подачек, сколько, по
 * предсказанию, успеет получить до порога стыда...
 */
```

Хорошо — только что это:

```ts
/**
 * Попрошайничать у ближайшего места для попрошайничества, пока не станет стыдно, но не больше
 * MAX_BEGGING_REWARDS_PER_VISIT подачек за заход
 */
```

Плохо — перечисляет предусловия методов, которые видны в коде:

```ts
/**
 * Деятельность бомжа: добывать на пойло. Бухает бомж не здесь, а в слое зависимостей, когда тянет.
 * Методы перечислены по приоритету: сдать бутылки, а если не получается — попрошайничать, а иначе —
 * собирать бутылки. Когда что получается, решают предусловия самих задач: сдать — если за бутылки
 * хватит на пойло, попрошайничать — если стыд ниже порога, собирать — если NPC унесёт ещё бутылку
 */
```

Хорошо:

```ts
/**
 * Деятельность бомжа: перебиваться. Методы перечислены по приоритету: сдать бутылки, а если не
 * получается — попрошайничать, а иначе — собирать бутылки
 */
```

Плохо — объясняет механику TypeScript:

```ts
/**
 * Занятие с его деталями. По полю activity TypeScript сужает тип деталей, поэтому потребностям не
 * нужно приводить детали к типу своего занятия
 */
```

Хорошо:

```ts
/** Занятие, от которого меняются потребности: его вид и детали */
```

Плохо — у помощника для тестов перечислено, что внутри, хотя хватает назначения:

```ts
/**
 * Создаёт потребности, у которых жизненная сытость и зависимость от пойла с переданными статусами
 */
```

Хорошо:

```ts
/** Создаёт потребности с указанными статусами */
```
