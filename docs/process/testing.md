# Тестирование

## Принципы

1. Тесты должны быть спецификацией проекта. Не должны использоваться формулировки тест-кейсов,
   которые не отражают причинно-следственные связи. Тест-кейсы пишутся в формате утверждений:
   "_возвращает_", "_вызывает_", "_выбрасывает_". Приветствуется использование шаблонных фраз:
   "если _условие_, _утверждение_". Если какой-то набор тест-кейсов повторяется при определённом
   состоянии, это состояние может быть обёрнуто в отдельный `describe`, который именуется по шаблону:
   "_При_ таком-то состоянии".
   Как отличить спецификацию от утверждения о значении — в разделе
   [Названия тестов](#названия-тестов).
2. На один тест должна приходиться одна-две проверки.
3. Избегаем happy path тестов. Лучше несколько атомарных тестов, чем один happy path
4. Придерживаемся принципа **A**rrange, **A**ct, **A**ssert.
5. Все данные для теста формируются в самом тесте. Не используем
   beforeAll, beforeEach, afterAll, afterEach - они усложняют понимание одного конкретного теста.
6. Значимые для теста моки, описываются в самом тесте. Незначимые, при необходимости, выносятся
   в отдельную константу и могут переиспользоваться между тестами. Главное, чтобы они создавались
   всегда новые для каждого теста. Например, если тест проверяет, что при определённом уровне голода
   NPC падает в обморок, npc должен быть создан в тесте, голод должен фигурировать в тесте, а все
   остальные данные, например, такие как жажда, бодрость могут быть указаны в константе.
7. В одном файле должна проверяться только одна фича. Тестовый файл не длиннее 150 строк: если
   длиннее, он разделяется на подфайлы по методам или подфичам, или разбивается на проверки при
   определённых событиях.
8. Тест проверяет только поведение тестируемого класса. Если класс создаёт объект через фабрику,
   тест проверяет, что фабрика вызвана с нужными параметрами и что класс использует то, что она
   вернула. Поведение созданного объекта проверяется в его собственных тестах и не дублируется. Тест
   фабрики проверяет только, что она возвращает экземпляр нужного класса.
9. Вспомогательные функции, которые используются в нескольких тестовых файлах — моки, фабрики данных,
   builder'ы, — лежат в `dev` пакета и экспортируются из его точки входа `dev/index.ts`, а не в
   `__tests__`. Так их видно и тестам самого пакета, и тестам пакетов, которые от него зависят.
   Функция, которая нужна только одному файлу, остаётся в нём.

## Названия тестов

Название теста — правило предметной области: почему так происходит. По нему читатель, который не
видит тела теста, понимает, как устроен мир. Значение, которое вернул метод, — только следствие
правила, а не само правило.

- **Правило, а не значение.** Если в названии есть только «возвращает 0» или «возвращает 100», а
  почему именно столько — нет, это не спецификация. Сначала называется правило, а значение, если
  нужно, — после двоеточия.
- **Без значений моков.** Числа из моков и данных теста живут в его теле, а если нужно, в
  комментарии рядом с проверкой объясняется, почему из них следует результат. Если в названии
  есть число из мока, скорее всего, это не спецификация.
- **Расчёт описывается, а не утверждается.** Если код что-то считает, тест называет, как считается,
  и проверяет это на нескольких входах, например таблицей `it.each`. Один тест «через сутки тянет»
  утверждает результат, но не говорит, как к нему пришли.
- **Без утверждений, которые вводят в заблуждение.** Название не должно подсказывать связь, которой
  нет: «если поели, тяга не меняется» звучит так, будто еда как-то связана с тягой, хотя правило —
  что не связана.

Примеры из ревью:

| Плохо                                                       | Хорошо                                                                                                                                                                                                      |
| ----------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Если выпили, возвращает 0                                   | Питьё не влияет на сытость: возвращает 0                                                                                                                                                                    |
| Если поели, возвращает 0                                    | Еда не влияет на тягу к алкоголю: возвращает 0                                                                                                                                                              |
| При максимальной силе выпившего NPC снова тянет через сутки | Удовлетворённость падает со скоростью, пропорциональной силе: при максимальной силе от MAX_SATISFACTION до CRAVING_BELOW за cravingMinutes. При силе $strength через $hours ч от 100 остаётся $satisfaction |
| Если NPC ожидает 60 попыток, не планирует подачек           | Если по ожиданию психики NPC не успеет получить ни одной подачки до BEGGING_SHAME_LIMIT, план не составляется                                                                                               |

## Отчёт о тестах

Тесты — спецификация, поэтому их удобно читать целиком, а не файл за файлом. CI публикует отчёт
Allure на GitHub Pages: дерево слоёв, пакетов, файлов, `describe` и тест-кейсов с результатами.
Отчёт `main` обновляется при каждом мерже и хранит историю прогонов: по ней видно, как менялось
число тестов и какие тесты нестабильны. Отчёт ветки пулл реквеста обновляется при каждом пуше и
показывает историю `main`: по ней видно, какие тесты новые. Ссылка на него есть в пулл реквесте, в
окружении `tests` (см. [CI и сборки](./ci.md)).

Локально тот же отчёт собирается так: `npm run test:report` запускает тесты и складывает
результаты в `allure-results`, `npm run test:report:generate` собирает из них отчёт в
`.allure/report`, а `npx allure open .allure/report` открывает его в браузере.
