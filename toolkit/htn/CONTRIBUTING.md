# @peetland/htn

HTN (Hierarchical Task Network) - это подход к планированию поведения NPC, где задача описывается
**иерархией**: сложная задача раскладывается на подзадачи, те - на ещё более простые и так вплоть до
самых примитивных действий. HTN предполагает что пользователь будет сам описывать задачи и способы
их декомпозиции, а планировщик только выбирает наиболее эффективный способ решения задачи при
текущем состоянии мира.

## Базовые понятия

- **Primitive Task** - простая задача, которую можно решить без дополнительных действий, например:
  идти к координатам, выполнить анимацию, подождать некоторое время и т.д. Такие задачи не
  преследуют никаких целей, а являются инструментом для их достижения
- **Effect** - эффект выполнения задачи, например для задачи "пойти к координатам", эффектом будет
  смена текущей позиции NPC на координаты. Эффектов может быть несколько. Например, если в мире
  реализована усталость, то помимо смены позиции, эффектом может быть уменьшение уровня усталости.
- **Compound Task** - сложная задача, которая преследует какую-то конкретную цель и имеет несколько
  методов реализации, в зависимости от предусловий.
- **Method** - способ решения составной задачи, состоящий из последовательности задач, как
  примитивных, так и составных. Например: метод задачи "Насвинячиться в дрысь" при соблюдении
  предусловия наличия водки в доме, декомпозируется до простых задач: "Пойти к холодильнику",
  "Взять водку", "Пить до посинения". Подзадачи метода могут зависеть от состояния мира: например,
  "Пойти к ближайшему магазину" — это "Пойти к координатам" с координатами того магазина, который
  ближе всего к NPC. Тогда вместо списка подзадач метод задаёт функцию, которая собирает их по
  состоянию. Планировщик вызывает её, только если предусловия метода подошли.
- **World State** - текущее состояние мира, на котором как раз и будут проверяться предусловия и
  при котором будет выполняться задача. В состоянии лежат данные и сущности, доступные только на
  чтение. Задачи их не меняют: эффекты пишут в копию и возвращают новое состояние.
- **Context** - контекст исполнения: мутабельные сущности, которым задачи отдают команды, например
  актор или инвентарь. Состояние мира задачи только читают, а командам подчиняется контекст.
  Контекст получают только методы задачи, которые что-то меняют: `start`, `update` и `stop`.
  `canExecute`, `applyEffects` и предусловия методов контекст не получают: они только читают
  состояние и считают эффекты, и живые сущности им не нужны.

Экземпляр задачи одновременно исполняет только один агент. Поэтому задача хранит состояние
исполнения в своих полях и сбрасывает его в `start`.

### Планировщик

Планировщик - это алгоритм, который принимает на вход составную задачу и текущее состояние мира. О контексте исполнения планировщик не знает. На
основе этих данных, ему нужно решить наиболее оптимальный способ решения задачи. Планировщик
перебирает методы составной задачи верхнего уровня, раскладывает эти методы на подзадачи проверяя
для каждой из задач предусловия. При этом, эффекты одной задачи применяются к состоянию и
предусловия следующей задачи проверяются уже с этими эффектами.

Здесь стоит обратить внимание читателя на то что составные задачи могут содержать другие составные
задачи в методах своего выполнения. Это означает что планировщик при планировании основной задачи,
будет рекурсивно планировать и вложенные задачи, выбирая из них наиболее подходящие.

Если вся цепочка подзадач метода может быть выполнена, то этот метод и будет превращён в план.
План - это набор задач, декомпозированных до примитивных. План является результатом работы
планировщика.

Если вместо задачи в методе оказалось `undefined`, например его вернул мок фабрики задач без
реализации, планировщик выбрасывает `TypeError` с именами метода и составной задачи, а не молча
обрезает план.

#### Шаги плана

План состоит из шагов (`PlanStep`). В шаге лежит примитивная задача (`task`) и узел разложения,
частью которого она запланирована (`isPartOf`). Узел (`PlanNode`) — это составная задача, метод,
которым планировщик её разложил, и родительский узел. У узла корневой задачи родителя нет, поэтому
цепочка `isPartOf` от любого шага приводит к корню, и по ней видно, почему план именно такой. Если
корневая задача — сама примитивная, у её шага `isPartOf` равен `null`.

Узлы создаёт планировщик, а не задачи: составная задача — переиспользуемый объект и не знает своего
родителя. На каждое разложение планировщик создаёт новый узел, поэтому одна составная задача,
запланированная дважды, даёт два разных узла, а задачи одного разложения — части одного узла.

### Исполнитель

Исполнитель - это сущность которая принимает на вход план и выполняет его задачи, последовательно их
запуская. В случае если задача не может быть выполнена, исполнитель прерывает своё выполнение и
передаёт управление снова планировщику, который должен перепланировать корневую задачу и составить
новый план на исполнение.

### Транзакции и мягкая остановка

Агент перепланирует сам, когда план закончился или упал. Если перепланировать нужно раньше,
например обстоятельства изменились и текущий план больше не нужен, агента мягко останавливают
методом `softStop()`. Агент передаёт просьбу исполнителю текущего плана и ничего не ждёт, а если
плана нет, останавливать нечего. Когда исполнитель остановился, агент в том же `update` составляет
новый план.

Но не каждую задачу можно бросить на середине. Бывают задачи из нескольких шагов, которые имеют
смысл только вместе: если остановиться после первого шага, мир останется в несогласованном
состоянии. Такую составную задачу помечают транзакцией (`transaction: true`), а если задачи
транзакции собираются на месте, их объединяют в `TransactionTask`. Мягкая остановка даёт
транзакции закончиться, а жёсткая `stop()` её не ждёт. Транзакция внутри транзакции — часть
внешней, а одна транзакция, запланированная дважды, — две разные транзакции.

Транзакция задерживает остановку, поэтому она должна быть короткой: только шаги, которые нельзя
разорвать.

### Параллельная задача

Исполнитель выполняет задачи плана строго по очереди. Если две задачи нужно выполнять одновременно,
например, ждать, пока повезёт, и всё это время проигрывать анимацию, их объединяют в
`ParallelTask`. Это примитивная задача из двух задач: основной и фоновой.

- Результат параллельной задачи — результат основной. Когда основная завершилась, фоновая
  останавливается.
- Если фоновая завершилась успешно, в следующем `update` она запускается заново. Так незацикленная
  анимация повторяется, пока идёт основная задача.
- Если фоновая завершилась ошибкой, основная останавливается, а параллельная задача завершается с
  `failed`.
- Эффекты фоновой задачи не учитываются, поэтому она не должна менять состояние.

Для планировщика параллельная задача — обычная примитивная, и в плане у неё один шаг. Её состав
видно в полях `main` и `background`.

Задачи не должны мешать друг другу. Ждать и проигрывать анимацию можно одновременно, а идти в две
стороны — нельзя.

## Пример HTN

Допустим, нам нужно реализовать NPC, который будет спать, если устал. И бесцельно блуждать пока не
захочет спать. Ниже представлены world state для такого NPC и его HTN:

```yml
world_state:
  energy: number # 0..100
  position: Vector2 # метры
  home: Vector2
  time: number # минуты

root:
  name: Live
  methods:
    - name: Rest (energy < 20)
      subtasks:
        - Rest:
          methods:
            - name: ToFaint (energy == 0)
              subtasks: [ApplyAnimation(Fall), Sleep(until 30)]
            - name: SleepAtHome (position = home)
              subtasks: [Sleep(until 90)]
            - name: GoHomeAndSleep (distance(position, home) >= 1)
              subtasks: [GoToPoint(home), Sleep(until 90)]
    - name: Wander (energy >= 20)
      subtasks:
        - Wander:
          methods:
            - name: RandomWalk (true)
              subtasks: [GoToPoint(random in radius 100 meters)] # точка выбирается при исполнении

primitive_tasks:
  - name: GoToPoint
    params:
      point: Vector2
    interrupt_when: energy <= 0 # по фактическому состоянию
    effects:
      - position = point
      - time += distance / 83.3 # 5 км/ч, минуты
      - energy = max(0, energy - distance * 0.1)
  - name: Sleep
    params:
      until: number # целевая энергия
    effects:
      - time += max(0, until - energy) * 6 # по актуальной энергии
      - energy = max(energy, until)
  - name: ApplyAnimation
    params:
      name: string
    effects: []
```

## Для тестов

Точка входа `@peetland/htn/dev` даёт помощники, которыми тесты задач проверяют план. Своих матчеров
нет: план переводится в простые данные, а сравнивают их обычные `toStrictEqual` и `toContainEqual`.

- `planSteps(root, state)` — составляет план и возвращает его шаги или `null`, если план составить
  нельзя, а `plan` — его задачи.
- `planTree(steps)` — структура плана: дерево, в котором составные задачи — с выбранным методом,
  признаком транзакции и детьми, а примитивные — их имена.
- `PlanStructureBuilder` — собирает ожидаемую структуру плана для сравнения с `planTree`:
  `primitive(name)`, `compound(name, method, build)` и `transaction(name, method, build)`. Детей
  составной задачи собирает функция `build`: она получает новый билдер и возвращает его.
- `planTransactions(steps)` — имена задач каждой транзакции плана по порядку.

```ts
import { PlanStructureBuilder, planSteps, planTransactions, planTree } from '@peetland/htn/dev';

const steps = planSteps(task, state) ?? [];

expect(planTree(steps)).toStrictEqual(
  new PlanStructureBuilder()
    .compound('sell-bottles', 'sell-in-nearest-collection', (sell) =>
      sell
        .primitive('go-to-coords')
        .transaction('hand-over-bottles', 'hand-over-bottles', (handOver) =>
          handOver.primitive('remove-item').primitive('add-item')
        )
    )
    .build()
);
expect(planTransactions(steps)).toContainEqual(['remove-item', 'add-item']);
```

Задачи сравниваются по именам, поэтому параметры задач проверяются моками фабрик задач.
